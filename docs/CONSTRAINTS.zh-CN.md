# 技术约束与避坑清单 (CONSTRAINTS.md)

> **这里放什么**：会在**本代码库**里咬人的坑——约束、陷阱、看着没问题其实有问题的地方。每条都带 **Why** 和 **Date**，因为一条失去理由的规则，会被下一个觉得它碍事的人删掉。

## 纠错该往哪写

| 纠错类型 | 写进 | 形态 |
|---|---|---|
| **技术坑**——"这个 API 在 X 情况下会炸"、"别动那个配置"、"那次调用会静默截断" | **本文件**，放进对应领域 | `约束 — Why：…（YYYY-MM-DD）` |
| **AI 行为习惯**——"测试命令别用全屏"、"函数尽量写纯函数" | [`AGENTS.md`](../AGENTS.md) 避坑清单 | 负面约束 |
| **业务规则** | [`SPEC.md`](../SPEC.md) | 规则正文 |
| **架构决策** | [`DECISIONS.md`](DECISIONS.md) | 背景 / 决策 / 影响 |

这个分工要守住：技术坑混进避坑清单会被行为规则淹没；行为规则混进本文件会读起来像代码有毛病。

## 条目格式

```markdown
- **<一句话约束>** — Why：<它防住的是什么故障>。（YYYY-MM-DD）
```

## 别这么干

- 别写没有 **Why** 的坑。下一个人会"顺手清理"一条没写理由的规则。
- 别把同一个坑记在两个领域。挑一个别人真会去找的地方。
- 别把类型系统或门禁已经强制的东西写进来——那是 `standards/TESTING.md` 的活。
