# 决策与演进时间线 (DECISIONS.md)

> 本文档用于以微日志（Lightweight ADR）的形式记录项目的重大架构调整、需求变更及背后的原因。
> **目的**：防止数周或数月后遗忘“当初为什么把那个逻辑改成这样”，杜绝需求反复横跳。

---

## 变更记录模板格式
```markdown
### [YYYY-MM-DD] [变更标题]
- **触发背景**：用户反馈 / 性能瓶颈 / 测试异常
- **核心决策**：将原本的 XXX 规则改为 YYY
- **对应 SPEC 章节**：SPEC.md 第 X.X 节
- **影响范围**：[列出涉及的模块或文件]
```

---

## 历史决策流

### [2026-09-22] 仓库脚手架初始化
- **触发背景**：创建 Vibe Coding Starter 通用规范模板。
- **核心决策**：确立 SDD（规范驱动）+ 双层门禁 + 自进化避坑清单为核心工作流。
- **对应 SPEC 章节**：全文档初始化。
- **影响范围**：全局。

### [2026-09-22] 强化防死扣局部跑偏与防真理源（SPEC）早产污染机制
- **触发背景**：实战开发中，AI 极易因用户某句话中的局部技术细节（如特定文件解析或算法）而反客为主，将局部支撑手段拔高为系统核心定位，导致真理源（SPEC.md）被过早污染，背离用户真实终极体验目标。
- **核心决策**：
  1. 在 AGENTS.md 引擎 1 中设立“主次校验拦截”：严禁死扣局部反客为主，必须永远以用户终极使用场景和产品体验为纲；
  2. 增加“防真理源早产与污染”规则：在实证调研未完成前，严禁将未经检验的技术假想写入 SPEC.md 核心定位；
  3. 在避坑清单中永久固化规则 11 与 12。
- **对应 SPEC 章节**：全局规范演进。
- **影响范围**：AGENTS.md。

### [2026-09-24] [示例] 严重度阶梯统一以 P0–P3 为准
- **触发背景**：不同审查环节可能输出两套分级（P0–P3 与 Critical/Important/Minor），并存会导致收敛判据混乱。
- **核心决策**：以 AGENTS/TESTING 的 P0–P3 为唯一阶梯；其余分级一律映射（Critical→P0/P1、Important→P1、Minor→P2/P3），停止准则统一走 DoD。
- **对应 SPEC 章节**：全局规范演进。
- **影响范围**：standards/EXECUTION.md §0、standards/REVIEWING.md 输出格式。

### [2026-09-24] [示例] 当实验推翻先前指令时，以实验为准
- **触发背景**：曾按文档先例给出一个修复指令（“清空某配置项”），但对照实验证明该形态同样导致故障。
- **核心决策**：停止执行字面指令，改为按实验证据的更彻底方案，并把“为何推翻原指令”的实验结果一并记档。
- **对应 SPEC 章节**：不涉及业务规范，属工程执行层。
- **影响范围**：docs/DECISIONS.md 记录格式范例；执行纪律见 standards/EXECUTION.md §5 事故条目。

### [2026-09-30] 按职责分层重组 + 全双语文档 + 规则总账
- **触发背景**：根目录堆了 8 份 Markdown，而另一些嵌在 `docs/` 下，分层标准不明；同一条规则（严重度阶梯、1 变 4、凭证卫生）同时在两三个文件里各写一份，已经开始漂移。仓库定位是开源模板，却只发中文文档。
- **核心决策**：
  1. 目录按职责分层：有约定位置要求的留在根目录；`standards/` 放方法，`docs/` 放项目记录，`templates/` 放可复制进新项目根的成品，`tooling/` 放脚本与测试；
  2. 新增 `standards/RULES.md` 规则总账：每条规则一个稳定 ID、一个唯一归属文件，由 `tooling/checks/check_docs.py` 物理守卫；
  3. 每份 Markdown 出两个镜像文件：`NAME.md`（英文正本，GitHub 默认渲染）与 `NAME.zh-CN.md`（简体中文）。中文为撰写源，英文与之镜像；
  4. 把 `templates/ci.yml` 提升为常驻的 `.github/workflows/ci.yml`，让脚手架自己验证自己；
  5. 回流 DaySpark 实战沉淀的四条通用门禁：正交验证、溯源验收、漂移守卫、棘轮基线。
- **对应 SPEC 章节**：全局规范演进。
- **影响范围**：整个仓库。
